3. What the review found

The 31 high risk issues (28 + 3) fall into six themes.

A. Nothing alerts anyone (7 HRIs)

OPS observability · OPS workload observability · OPS event response · OPS ready to support · REL monitor resources · REL withstand component failures · Serverless OPS health

There is a good CloudWatch dashboard, X-Ray tracing and structured logs — but not one CloudWatch alarm in the template. Lambda errors, API 5XX responses, throttles, messages in the dead-letter queue and stream lag are visible only to someone who happens to open the dashboard. API Gateway access logs are off, there are no KPIs/SLOs, and there's no playbook for "what do I do when X happens".

B. The AWS account's security baseline needs work (4 HRIs)

SEC securely operate · SEC identities · SEC detect and investigate events · SEC incident response

These came from read-only checks of the account (identity, logging and threat-detection settings), not from the repository. The specific results are kept private on purpose — a public list of an account's missing controls is a map for an attacker. What can be said: the most important findings of the whole review were here, about access to the account itself rather than the app, and they are first in the improvement plan. In addition, the app has no API Gateway access logs or WAF logs and no incident response plan, and the account is a single account shared by several projects.

C. Changes go straight to production (5 HRIs)

OPS mitigate deployment risks · Serverless OPS lifecycle management · SEC application security · SEC protect compute · Serverless SEC application security

Tests and lint gate every deploy, but there is one environment (prod) in one account, every deploy shifts 100% of traffic at once (no Lambda aliases / canary), a failed smoke test doesn't roll back, and dependencies are never scanned (no Dependabot, no Amazon Inspector).

D. Cost is designed well but not governed (5 HRIs)

COST cloud financial management · COST govern usage · COST monitor usage · COST pricing models · COST data transfer

The design is cost-aware (toggles, teardown, estimate per scenario), but there is no AWS Budget or cost anomaly alert in the account, the project tag is not confirmed as a cost allocation tag, and pricing models and data transfer weren't analysed.

E. Resilience is built in but not tested (6 HRIs)

REL mitigate interaction failure · REL service quotas · REL back up data · REL fault isolation · REL test reliability · REL plan for DR

What exists: global table with < 1 s RPO, PITR, a scripted rebuild proven in 4 m 38 s. What's missing: boto3 timeouts are longer than the function timeout, GetOrder has no fallback when DAX is down, no reserved concurrency (one route can starve the others), OrderStats has no backup or rebuild script, a PITR restore has never been tested, there is no RTO, and nothing was ever load tested.

F. Things a team would have written down (4 HRIs)

OPS priorities · OPS organization · PERF process · SEC data classification

No threat model, no performance KPIs or load test, no data classification. Partly expected for a one-person project — but a threat model and a one-page data classification are cheap and useful.

Medium risks worth knowing

  • POST /orders is not idempotent — a client retry after a timeout creates a second order, and order lines are written with batch_writer (not a transaction), so a failure mid-way can leave a partial order (REL prevent interaction failure, Serverless REL resiliency).
  • WAF has only a rate-based rule — no AWS managed rule groups (SEC network protection).
  • The CloudFormation execution role has AdministratorAccess (assumable only by CloudFormation), with no permission guardrails (SEC permissions).
  • No API usage plans / per-client quotas (Serverless REL inbound request rates).

6. What I learned about the process

  1. The tool doesn't look at anything. It never scans your account or code — every answer comes from you. The real work is collecting evidence; the tool turns it into a risk view and a report.
  2. The most serious findings weren't in the repository. They came from a handful of read-only CLI calls against the account. A code-only review would have missed them.
  3. Decide what to publish. Findings about the account's own security settings stay private; the public write-up names the theme, not the specific gaps.
  4. A first review shows lots of high risks — that's normal. The Framework is written for organizations running production systems. A question is high risk when an important best practice is missing, even if most of the others are in place: "mitigate interaction failure" has 4 of 7 practices and is still high risk (no timeouts below the function timeout, no graceful degradation). The count matters less than the prioritised list it produces.
  5. "Not applicable" is a precise tool. Marking 18 choices that can't exist here (VPN to on-premises, load balancers, accelerators…) as not applicable, each with a reason, moved high risks from 30 to 28. Using it for real gaps ("we have no budget") would just hide risk.
  6. Answers as code pay off. 66 answers in two JSON files can be reviewed in a pull request, re-applied in seconds, and diffed between milestones. The tool's console stays the place to read the review.
  7. CLI gotchas: list commands return 10 items by default and the CLI doesn't page through this service automatically (47 of 57 questions silently missing); boto3 has no paginators for it; the PDF report arrives base64-encoded and needs whitespace stripped on Windows.

7. Next step

Work through the improvement plan in small pull requests. After each one, update the affected answers in answers/*.json, run scripts/wa_review.py apply, and when a group is done save a new milestone (v1.1-…) and regenerate the chart with scripts/risk_chart.py to compare against this baseline.
